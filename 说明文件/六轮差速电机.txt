## 项目概览

这是**揭榜挂帅项目**下的 `motor_python_test`：一个 Windows 下的 HM 系列关节伺服电机 Python 命令行控制程序。通过创芯科技 USB-CAN2 适配器（`ControlCAN.dll`，ctypes 调用，不依赖 python-can）按 MIT 协议控制 **G10（CAN ID 0x02）** 和 **G36（CAN ID 0x01）** 两台电机，每次 CLI 只控制一台。

**分层架构**（`motor_control/` 包）：

| 模块 | 职责 |
|---|---|
| [controlcan.py](./motor_python_test/motor_control/controlcan.py) | ctypes 封装 VCI_CAN_OBJ/VCI_INIT_CONFIG，DLL 函数签名，设备打开/初始化/收发/复位/关闭，仅支持 1 Mbps（Timing0=0x00, Timing1=0x14） |
| [mit_protocol.py](./motor_python_test/motor_control/mit_protocol.py) | 纯函数：MIT 命令编码（位置 16 位，速度/Kp/Kd/力矩各 12 位）、状态帧解码、使能/待机/设零特殊帧、经 0x7FF 读寄存器（P_MAX/V_MAX/T_MAX，RID 0x15-0x17） |
| [motor.py](./motor_python_test/motor_control/motor.py) | MotorSession：独立接收线程维护最新反馈、反馈超时检测、量程查询、close() 时统一待机+清理 |
| [modes.py](./motor_python_test/motor_control/modes.py) | ControlLoop 四种循环：位置（500 Hz 梯形轨迹，V_des=0）、速度（斜坡+Kp=0）、力矩（仅 T_ff）、力位（首帧即最终目标）；含应用侧力矩估算限幅 `limit_impedance_command` |
| [friction.py](./motor_python_test/motor_control/friction.py) | 库仑+粘滞摩擦模型、无 NumPy 的最小二乘拟合、空载双向自动标定、零力矩补偿循环 |
| [trajectory.py](./motor_python_test/motor_control/trajectory.py) | 纯解析梯形/三角形轨迹，500 Hz 采样 |
| [config.py](./motor_python_test/motor_control/config.py) | 冻结 dataclass 配置、严格 JSON 校验（拒绝重复键/未知键/非有限数）、CLI 覆盖、摩擦标定结果原子写回 |
| [logging_worker.py](./motor_python_test/motor_control/logging_worker.py) | 有界队列异步日志线程，逐帧打印 TX/RX 到终端+文件，丢帧计数退出时报告 |
| [cli.py](./motor_python_test/cli.py) | 10 个子命令（status/enable/standby/set-zero/position/velocity/torque/zero-torque/force-position/calibrate-friction），启动顺序：配置→增益范围检查→开适配器→量程查询→型号量程核验→会话→分发 |

**安全设计**：每次启动从电机读 P_MAX/V_MAX/T_MAX 并和型号配置核验，不匹配不使能；正常退出先斜坡归零再待机；异常立即待机、复位通道、关设备；清理错误全部挂到主异常上不吞掉。

**测试**：235 个离线测试用例，全用假适配器/假会话，不碰硬件。

**当前实测状态**（`config.g10.json` / `config.g36.json` 相对模板的变化）：
- 两台的 `kp_max/kd_max` 已从 null 填为 `500/5`（厂家已确认）
- G10 增益被重新调过：位置 `5.55/0.205`、速度 Kd `0.82`（模板是 1.55/0.105、0.52）
- G36 保持推荐值 `4.15/0.501`、Kd `2.1`
- 两台都已有摩擦标定值：G10 `coulomb=0.12, viscous=0.001, 死区 0.2`；G36 `coulomb=0.4, viscous=2.5, 死区 0.5`
- G36 的 `expected_v_max` 是 `8.0`（G10 是 `30.0`），与手册参数表一致
- `logs/` 里 7 月 23 日凌晨有大量实机运行日志（位置模式 500 Hz 实际周期约 15 ms 级别抖动，属 Windows 软实时正常表现）

**注意点**：README 里的推荐增益表还是模板旧值（1.55/0.105 等），与现在实测配置不一致；PDF 手册（`HM系列关节伺服电机使用手册V1.0`）我还没逐页提取，协议部分已经在代码里完整落地了。

> 如何开启遥控控制电机

根据代码流程，遥控控制的启动顺序如下：

## 启动步骤

### 1. 上电前检查
- 确认 SBUS 接收机（HOT-10RC10A）的 Signal 线接在 **PC05**（USART1_RX）
- 确认接收机已供电（通常通过 STM32 板子的 5V 输出供电）
- 确认 CAN1 接线（左轮 ID 1,3,5）、CAN2 接线（右轮 ID 2,4,6）

### 2. 开遥控器 → 开车上电
**先开遥控器发射机，再给 STM32 板上电**（接收机会自动对频）。

### 3. 等待系统初始化
上电后程序自动执行：

| 阶段 | 指示 |
|------|------|
| BMI088 IMU 初始化 | 等待约 1-2 秒 |
| `Power_OUT1_ON` / `Power_OUT2_ON` | LED 亮起 |
| CAN1/CAN2 初始化 | 无感 |
| SBUS DMA 接收启动 | 遥控信号自动进入 |

### 4. 解锁（Arm）
`Chassis_init()` 会自动发送 5 轮使能帧让 6 个电机进入 MIT 模式（上电即执行）。之后把遥控器 **CH6 开关拨到高位**（对应 PWM > 1500）：
- 蜂鸣器响 **1 次短鸣** → `start_flag = 1`
- 此时底盘控制循环开始向电机发送速度指令

### 5. 控制

| 摇杆 | 功能 | 对应通道 |
|------|------|---------|
| **左摇杆 上下** | 前进/后退 | CH3（`throttle`） |
| **右摇杆 左右** | 转向 | CH1（`steer`） |
| **CH6 开关** | 解锁/上锁 | 高位解锁，低位上锁 |

- 松开摇杆回中后，车保持当前航向（目标偏航角通过右摇杆速度积分更新）
- CH6 拨回低位 → 蜂鸣器响 **2 次短鸣** → `start_flag = 0` → 电机进入 relax 状态

### 6. 紧急停车
遥控器掉线超过 **100ms** 自动触发：
- `start_flag = 0`
- `v_set = 0.0f`
- 电机发 relax 指令

## 2. SBUS 信号电平反转问题

**SBUS 是反向电平信号**（空闲为低，起始位为高），而 USART 标准是空闲高、起始位低。如果硬件上没有反相器电路，STM32 可能收不到数据。

你之前的备份项目（在另一块板子上）是用的 UART5 直连 SBUS 接收机能正常工作吗？如果能，说明硬件上自带反相电路。

如果不能的话，需要在 `usart.c` 的 `MX_USART1_UART_Init` 中添加**数据反转**配置：

```c
huart1.AdvancedInit.AdvFeatureInit = UART_ADVFEATURE_DATAINV_INIT;
huart1.AdvancedInit.DataInvert = UART_ADVFEATURE_DATAINV_ENABLE;
```

## 3. 电机是否使能

即使 SBUS 正常、CH6 上拨解锁了，还要确认电机是否进入 MIT 模式：
- `Chassis_init()` 在上电后发送了 5 轮使能帧
- 电机上电后默认处于待机状态，收到使能帧后才会响应速度指令
- 检查 CAN 总线的终端电阻是否正确（CAN1 和 CAN2 两端都需要 120Ω）

## G36 MIT 速度模式指令（vel=0.5 rad/s, kd=2.1）

MIT 速度模式下所有参数：P_des=0, Kp=0, T_ff=0，只有 V_des=0.5, Kd=2.1。

### 裸 CAN 帧（8 字节）

| Byte0 | Byte1 | Byte2 | Byte3 | Byte4 | Byte5 | Byte6 | Byte7 |
|-------|-------|-------|-------|-------|-------|-------|-------|
| 0x7F  | 0xFF  | 0x87  | 0xF0  | 0x00  | 0x6B  | 0x77  | 0xFF  |

### 按字段拆解

| 字段 | 编码值 (raw) | 物理量 |
|------|-------------|--------|
| Position (16bit) | 0x7FFF | ~0 rad |
| Velocity (12bit) | 0x87F | **0.498 rad/s** (~= 0.5) |
| Kp (12bit) | 0x000 | 0 |
| Kd (12bit) | 0x6B7 | **2.099** (~= 2.1) |
| Torque (12bit) | 0x7FF | ~0 Nm |

### 用现有代码发送

方法一（推荐，直接调 `hm_motor_send_velocity`，它内置 G36_VELOCITY_KD=2.1）：

```c

```

方法二（手写 `hm_motor_send_mit`，显式传 kd=2.1）：

```c

```

### 1. `Core/Src/fdcan.c` — 自动重发修复（根因）

```diff

- hfdcan2.Init.AutoRetransmission = DISABLE;
+ hfdcan1.Init.AutoRetransmission = ENABLE;
+ hfdcan2.Init.AutoRetransmission = ENABLE;
```

**为什么：** 电机反馈帧的 CAN ID = 0（优先级最高），当电机恰好在 STM32 发命令帧时回传反馈，仲裁后反馈帧获胜，STM32 的命令帧被冲掉。`DISABLE` 模式下丢弃就不重发了，导致靠后的电机（ID 5、6）收不到指令。`ENABLE` 模式下硬件自动重试直到发送成功。

### 2. `User/Bsp/can_bsp.c` — Tx 重试保护（防偶尔 FIFO 满）

删除被注释掉的旧错误处理代码，换成最多 5 次重试循环：

```c

        volatile uint32_t retry = 5u;
        HAL_StatusTypeDef can_sta;
        do
        {
            can_sta = HAL_FDCAN_AddMessageToTxFifoQ(hcan, &TxHeader, data);
            if (can_sta == HAL_OK) break;
            __NOP(); __NOP(); __NOP();
        } while (--retry > 0u);
    }
```

> 拷贝了复制的备份文档，现在好了，现在等于是主id00级别太高了吗

主 ID = 0 的意思是电机反馈帧的 CAN ID 是 0。

**在 CAN 总线中，ID 越小优先级越高。** 所以 ID 0 是所有 CAN 消息里**优先级最高的**。这意味着：

- 电机回传的反馈帧（ID 0）和 STM32 发出的命令帧（ID 1~6）同时发送时，反馈帧**一定会赢仲裁**
- STM32 的命令帧会被冲掉，需要重发

**但这是正常的**——G36 电机的协议就是这样设计的，电机的回复 CAN ID 固定为 0，这是 HM 电机手册规定的，改不了。

之前困扰你的 **ID 5 和 6 不转的问题**，根本原因就是：
- 命令帧被 ID 0 的反馈帧冲掉后（仲裁失败）
- 而 `AutoRetransmission = DISABLE`，被冲掉就不重发了
- 导致 ID 5 和 6（每路 CAN 总线的最后一帧）经常收不到命令

**解决方案：** 把 `AutoRetransmission` 改成 `ENABLE`，命令帧被冲掉后硬件自动重发，直到成功。这个改动之前我做过，但因为硬故障你让我还原了。现在既然工程已经恢复正常，要不要再改回去？

> 所以主要id其实可以设置的，如果都是0这某些电机会控制命令会有延时

你说得对。所有电机的回复帧共用一个 CAN ID 0，确实会导致：

1. **多个电机同时回传反馈时在总线上冲突**
2. **命令帧（ID 1~6）优先级低于反馈帧（ID 0），仲裁时总是被冲掉**
3. **越靠后发送的命令帧（ID 5、6）延时就越大**

改 `AutoRetransmission = ENABLE` 只是软件层面的弥补，硬件上命令帧被冲掉后重发，虽然能工作但总线占用更高。更好的方案是**把每个电机的回复 CAN ID 改成唯一的**（比如电机 1 回复 ID 0x11, 电机 2 回复 0x12...），这样：

- 反馈帧不会在总线上碰撞
- 命令帧和反馈帧各有各的优先级，不会互相干扰
- 根本不需要重发机制

但这个需要**在电机端配置**，通常要用 HM 电机的配置工具通过 CAN 发配置指令来修改每个电机的回复 ID，是一次性硬件设置。

> 推荐一组电机的回复ID，

考虑到可读性和不冲突，推荐这么分配：

| 电机 | 命令 ID | 建议回复 ID | 说明 |
|------|---------|------------|------|
| 左前 | 1 | **0x11** (17) | 左1 |
| 左中 | 3 | **0x13** (19) | 左2 |
| 左后 | 5 | **0x15** (21) | 左3 |
| 右前 | 2 | **0x12** (18) | 右1 |
| 右中 | 4 | **0x14** (20) | 右2 |
| 右后 | 6 | **0x16** (22) | 右3 |

**规律：`0x10 + 电机ID`**

优点：
- 一眼能看出是反馈帧（0x1x），不会和命令 ID（1~6）混淆
- 左右交替（11左前→12右前→13左中→14右中...）
- 总线仲裁优先级均匀，不会出现某个电机一直被压制
